## What is Lumia?

Lumia is a cross-platform Electron desktop app for screen capture, screen recording, annotation, and sharing (Windows + macOS). Built with Electron 42, React 19, TypeScript, Tailwind CSS 4, and Konva.

Headline features:
- Image capture: region, active window, active monitor, fullscreen. The screen is **frozen at hotkey time** (native GDI snapshot on Windows, warm ScreenCaptureKit snapshot on macOS 14+) so captures preserve transient UI like tooltips/popovers
- Scrolling capture: its own capture kind beside Image/Video, with two methods — a companion **browser extension** (exact DOM scroll offsets over a localhost WebSocket bridge, no stitch guessing; `extension/` at the repo root) and the classic **screen scroll** (synthetic wheel + FFT/SAD overlap stitching) that works on any app
- Video recording: region / window / fullscreen with floating toolbar + visible region border, plus a live drawing overlay during recording; output WebM is remuxed seekable via bundled ffmpeg
- Annotation canvas (Konva) with re-editable vector layers stored alongside originals and R2-hosted stickers
- Desktop wallpapers from Wikimedia Commons or Wallhaven (Settings › Wallpapers, no API keys)
- Workflow pipeline: after-capture → upload → after-upload, configurable per template
- Built-in uploaders: Cloudflare R2 (baked credentials, streaming multipart) and Google Drive (OAuth, with a Google Picker folder browser)
- System tray, global hotkeys, launch-at-startup, auto-update via Cloudflare R2

Everything still open (reviews left, untested work, parked items, temporary code, questions) is listed in `design/OPEN-QUESTIONS.md`. Update it when an item opens or closes.

> If `pnpm dev` crashes at startup with `require('electron')` returning a path / `app` undefined, or a V8 `snapshot_data() != nullptr` assertion, check that `ELECTRON_RUN_AS_NODE` is **not** set in your environment — when present (even empty) it makes the Electron binary run as plain Node.
>
> A dev build runs on its own profile, `<appData>/lumia-history-dev` (`electron/dev-profile.ts`, imported first in `index.ts`), so `pnpm dev` and the installed app can run side by side: they used to share `%APPDATA%\Lumia` (package `name` and `productName` collide on case-insensitive filesystems) and therefore the single-instance lock, so the dev instance quit and the installed app came to the front. An explicit `--user-data-dir` still wins: `pnpm exec electron-vite dev -- --user-data-dir=$HOME/.lumia-dev`. The profile **must be inside the home directory**: the `lumia-media://` protocol only serves files under `homedir()` and the save folders (`isAllowedPath` in `capture-folder.ts`), so a profile in `/tmp` breaks every thumbnail and video (403, logged as `[lumia-media] refused path outside the home directory and save folders`). **All thumbnails broken although the profile is in the home directory** (files present in `<profile>/thumbnails/`, rows in `history.json` point at them): reload the renderer with Cmd+R (Ctrl+R) in the dev window, which fixed it when it happened on 2026-11-18 right after restarting `pnpm dev`. The `lumia-media` handler and the built app load the same thumbnails fine, so it is a dev-instance load glitch whose cause isn't known; try the reload before debugging. A fresh profile has empty history; to see your captures, copy `history.json`, `settings.json`, `templates.json` and `thumbnails/` from the installed profile (`~/Library/Application Support/Lumia` on macOS, `%APPDATA%\Lumia` on Windows). Deleting a history item in dev still deletes the real file in the save folder (`~/Pictures/Lumia` unless Settings › General › Save to says otherwise). Dev builds show a "D" badge on the tray icon (`resources/tray-dev/`, made by `scripts/make-dev-tray-icons.py`).
>
> **Memory**: every launch logs a per-process breakdown (`[mem] startup +10s` / `+60s` from `electron/mem-metrics.ts`) — the browser process, GPU process, the main renderer and one renderer per pooled overlay are listed separately. Set `LUMIA_MEM_LOG_INTERVAL_MS=30000` to keep sampling while profiling.
>
> **Capture latency**: every region / window / monitor capture logs one `[capture-trace]` line (`electron/capture-trace.ts`) with ms-since-hotkey marks — `hide`, per-display `grab` / `srgb`, `freeze`, `sent` (frames pushed to the overlays), and `reveal` per display (overlay visible). Check it before and after touching the freeze/overlay path. Recordings log one `[record-trace]` line (`electron/video.ts`): ms from the pick in the overlay to `source`, `toolbar created` and `toolbar shown` (the countdown visible; ~20 ms since the toolbar and the screen ids are prepared while the overlay is open, 2026-11-24).
>
> **Dock (temporary)**: `[dock-trace]` lines in `~/Library/Logs/lumia/main.log` (`electron/dock-trace.ts`, 2026-11-27) log every Dock-related step: `hideDock` / `showDock` and `app.dock.show()`, focus steals, did-become / did-resign-active, main window show / hide, `restoreFromOverlayCancel`, focus handed back, the tray's policy switch, the Swift helpers' spawns. Kept in to catch what sometimes leaves an auto-hidden Dock slid up; when it happens, note the time and read the lines before it. Remove with the fix (OPEN-QUESTIONS › Temporary code).

### Releases

Releases are produced by **GitHub Actions** (`.github/workflows/release.yml`), not local scripts. Cut a release by adding the release's notes to `src/whats-new.ts` (shown in Settings › Release notes; one entry per release, written from the changelog, its notes ordered new, improved, fix, maintenance; Settings shows them as written and folds older minor lines into one "Version X.Y" behind Show more; the 3.0.0 entry and the missing 2.6.6 one are already in, so the 3.0.0 release commit only sets that entry's `date`), bumping `version` in package.json, committing as `Release version X.Y.Z` **with the user-facing changelog as the commit body** (the GitHub release page is built from that body; a bare commit falls back to the commit subjects since the previous tag), then pushing tag `vX.Y.Z`. A `checks` job runs `pnpm test` and both `tsc --noEmit` first (2026-11-27; macOS runner, one test relies on POSIX folder permissions), and both release jobs wait for it: `pnpm build` alone doesn't type-check. Both `build:win` and `build:mac` skip code-signing locally (`CSC_IDENTITY_AUTO_DISCOVERY=false`); CI signs via repo secrets:
- Windows: **Azure Trusted Signing** — `AZURE_TENANT_ID` / `AZURE_CLIENT_ID` / `AZURE_CLIENT_SECRET` (CLI auth) + `AZURE_PUBLISHER_NAME`, `AZURE_TRUSTED_SIGNING_ENDPOINT`, `AZURE_CODE_SIGNING_ACCOUNT_NAME`, `AZURE_CERT_PROFILE_NAME` (injected into `azureSignOptions` by `electron-builder.cjs`; if any is missing the config omits `azureSignOptions` and the build proceeds unsigned)
- macOS: `CSC_LINK` (base64 .p12) + `CSC_KEY_PASSWORD`, plus `APPLE_*` env vars for notarization

`build/notarize.cjs` exits cleanly when notarization credentials are absent (so local unsigned builds still succeed). Published artifacts go to a Cloudflare R2 bucket served at `https://release.lumia.asia` (S3 publisher uploads, `generic` provider for client downloads). `electron-updater` polls `latest.yml` / `latest-mac.yml` from that origin every 4 hours. The 1.2.x line published to GitHub Releases as well; 2.0.0+ is R2-only — see `electron-builder.cjs` for the publish array.

## Architecture

### Process Model (Electron)

- **Main**: `electron/index.ts` — app lifecycle, all `BrowserWindow` factories, autoUpdater wiring, top-level IPC. `ipcMain.handle` calls are split across `index.ts`, `capture.ts`, `video.ts`, `scroll-capture.ts`, `stickers.ts`, `wallpapers.ts`, and `annotation.ts`.
- **Preload**: `electron/preload/index.ts` — single `contextBridge.exposeInMainWorld('electronAPI', {...})` whitelist
- **Renderer**: `src/` — React SPA with hash routing

`contextIsolation: true`, `nodeIntegration: false` everywhere. All renderer↔main traffic flows through the preload bridge.

**Adding a new IPC channel**: update three places in order, otherwise TS will fail at the call site:
1. The relevant setup module (`electron/index.ts`, `capture.ts`, `video.ts`, etc.) — add `ipcMain.handle('channel-name', ...)`
2. `electron/preload/index.ts` — add the method to the `contextBridge` whitelist
3. `src/electron.d.ts` — add the TypeScript signature to `Window.electronAPI`

Keep the bridge to what the renderer calls: an unused method is still reachable from every window, the overlays included (17 unused ones and their handlers were removed on 2026-11-27: file read, open path, quit, reload, the old recording and navigate calls). `scroll-extension:open-folder` and the extension status calls have no caller right now on purpose: they belong to the Dashboard launcher that is parked.

| `scroll-capture.ts` | Classic scrolling screenshot — multi-frame scroll loop with FFT-based overlap detection (`fft.js`). | `extension-bridge.ts` | Localhost WebSocket server (`ws`, ports 51763–65, extension-origin-only) for the companion browser extension. Theme (2026-11-26): `setExtensionTheme({ mode, roles })` (called from `applyThemeChrome` in `index.ts` on every theme change, with `pageRoles` from `browser-page.ts`) sends `{ type: 'theme' }` to every client and again on each `hello`; the extension keeps the last one in `chrome.storage.local` and draws its popup, status toast and Region picker with it (STYLEGUIDE › Browser extension). Old extensions ignore the message. Runs extension full-page captures — the app hides for the duration (like every other capture mode; no app-side progress dialog), the extension focuses its window (with a native SetForegroundWindow / AppleScript assist from the app, since the OS denies foreground to background processes), locks page interaction behind an invisible blocker + a small status pill (progress + Stop & save button that exports the frames collected so far; "header" bars — top < 20px, not reaching the viewport bottom — and offscreen/overflow-hidden-parent cases stay on the hide pipeline, full-screen fixed overlays are left alone to tile), re-runs the fixed/sticky neutralization sweep before **every** frame (sticky add-to-cart bars / chat bubbles / "Back to top" buttons that mount — or only become fixed — after the page scrolls get hidden mid-capture; overlays are hidden with `opacity:0` **and** `visibility:hidden` — visibility alone leaks, since a descendant with its own `visibility: visible` rule pokes back through a hidden ancestor and repeats down the stitch), runs a three-point pinned-chrome probe (element rects measured at top/bottom/middle scroll; anything holding its exact viewport position while content scrolls under it — JS-pinned sidebars, transform-pinned wrappers, shadow-DOM sticky — joins the hide list, which matters because a full-height pinned column spans the middle of the viewport where the stitch-time edge crops can't reach), then scrolls in overlapped steps (GoFullPage-style, extended to both edges: `meta.overlap` — 320 px doc / 180 px pane — is discarded at stitch time as `overlap − bottomCrop` off the top of every frame after the first plus `meta.bottomCrop` — 120 px doc / 80 px pane — off the bottom of every frame except the last, so viewport-pinned elements the in-page neutralization missed — JS/transform-pinned headers, shadow-DOM sticky, scroll-triggered "Back to top" buttons that appear only after the prep scan — can't repeat) and streams PNG frames + exact offsets back, so stitching is a plain buffer copy. For inner-pane apps (Gmail/Drive/Docs — page doesn't scroll, a middle `<div>` does) the stitch composites full-width: header/footer/side-margins come from frame 0 (chrome preserved, not cropped away — `stitchElementScroller`) while only the pane column is scroll-stitched; whole-document pages use `stitchDocumentScroller`. The finished image is delivered through `sendCaptureToEditor` (the shared capture path: watermark, clipboard, save-to-disk, history, editor navigation / notification) — NOT the classic scroll's `scroll-capture:*` dialog events. Captures also start from the extension's toolbar popup (`popup.html`) which offers three modes — **viewport** (one frame), **fullpage** (scroll + stitch), **region** (in-page element picker: hover highlights the element under the cursor — including inside same-origin iframes (the picker attaches to child docs + tracks each frame's offset) — a path bar at the top shows where the part sits (breadcrumb; ↑ / ↓ or a click on a step move out / in, ← / → to the part before / after, same-size nested parts merged into one step, empty overlay layers and `pointer-events: none` skipped; `design/REGION-PICKER.md`, 2026-11-27) — commit on mousedown, SCROLLS tag = scrollable → crop to that element via `stitchCroppedRegion` — scroll-stitched if it scrolls, else a single frame, no chrome) — threaded through `capture-request`/`capture-start` as `mode`. The scroll hotkey asks the browsers which one is in front (`focus` → `focus-result` with `chrome.windows` `focused`, 2026-11-27) and captures that one; an explicit extension capture with several browsers connected shows a picker with live tab previews (`scroll-extension:pick` event + `scroll-extension:previews` / `scroll-extension:start-with` IPC). Each step logs one `[ext-bridge]` line (request, start, meta, done / error / cancel, focus assist). Connection (2026-11-27): Lumia terminates every client at `before-quit` (ws 8's `server.close()` leaves open sockets alone, so the extension saw the close only when the process exited); the extension's service worker retries every 2s while disconnected (on top of its 30s alarm) and tells an open popup about connection and theme changes (`lumia-status`). Any extension origin may connect (not pinned to Lumia's own id, OPEN-QUESTIONS › Parked). ### Window Management

- **Main window**: 1250×700 (min 900×600), frameless, `#131313` background. macOS uses `hiddenInset` with traffic lights at `{x:20, y:19}` on the AppBar (no title bar); Windows uses native overlay controls (`titleBarOverlay`).
- **Overlay windows**: One transparent fullscreen `BrowserWindow` per display, `alwaysOnTop: 'pop-up-menu'`, `setVisibleOnAllWorkspaces(true, { skipTransformProcessType: true })`, `roundedCorners: false` (macOS masked a frameless window's corners away), and on macOS `setHiddenInMissionControl(true)` (they stay shown at opacity ~0 all session, so Mission Control would otherwise list a full-screen "Lumia Overlay" window; the recording toolbar, border and annotation overlay get the same call). A 100 ms cursor-poll switches the "active" overlay as the cursor moves between displays; inactive overlays use `setIgnoreMouseEvents(true, { forward: true })` to pass clicks through to the active one. The `overlay:drawing` IPC locks the active display while the user is drawing a region so the cursor poll can't yank focus mid-drag. The pool is pre-created at startup and **parked** at opacity 0 between captures (instant reveal); parking also sends `overlay:frozen-bgra-changed` `null` so the renderer drops the previous snapshot and its full-screen `<canvas>` backing store. Each parked window still costs ~28 MB in the GPU process (its full-screen compositor surface) plus a ~35 MB renderer; `win.hide()` was measured **not** to release the GPU part — only destroying the window would, at the price of the ~300–500 ms cold start on the next capture. On reveal Lumia takes activation (`app.focus({ steal: true })`) so the overlay owns the cursor and Esc (the Video overlay too since 2026-11-26; it only focused its window before); activation lands after `app.focus()` returns and macOS then gives the key back to the window that last had it, so `did-become-active` refocuses the overlay in use while overlays are open (2026-11-26). A known bug fixed 2026-11-27: on two displays, an overlay opened from the menu bar of the screen without Lumia's window turned its camera into the arrow on the first mouse move (the installed 2.6.5 too); the cause was the other screen's pooled overlay, never opened since launch, still in its "active" first state with a cursor request of its own (the page now starts inactive, see `overlay.html` below). The app in front is noted (`window-at-point` `front`) and gets activation back when the session ends with no Lumia window to show (`returnFocusToPreviousApp`). Mission Control over an open overlay: a 100 ms `mc` poll; the overlays step aside (snapshot dropped, click-through, `overlay:aside`), and when it closes Image takes a fresh snapshot and activation is asked back for 2.5 s (`did-become-active` / `did-resign-active` tracked; `win.isFocused()` can't tell). The overlays get the full theme (`useFullTheme`) and the current theme at every open.
- **Recording windows**: `RecorderHost` (hidden, owns the stream), `RecordingToolbar` (floating controls), `RecordingBorder` (visual outline), and a fullscreen annotation overlay (`annotation.ts`, toggled interactive via `annotation-overlay:set-interactive`) — all created and torn down by `video.ts`. The toolbar's window is created with `enableLargerThanScreen`, like the capture overlay, the border and the drawing layer (2026-11-27): macOS keeps a frameless window's top below the menu bar when it comes on screen unless it has that option (its level doesn't lift it), so the toolbar sat at the menu bar's bottom, its bar 4px under the overlay's. Since 2026-11-24: the toolbar is built hidden while the Video overlay is open (`prepareVideoPick`, with the screen source ids) and shown at the pick, always where the overlay's bar was (centred, at the same `captureBarTop`; `video.ts` places the window that minus the 6px the bar sits inside it, `TOOLBAR_BAR_INSET`); its countdown runs from the show (`toolbar:state` `countdown`, or `toolbar:is-shown` if the page was late) while the host acquires the stream, and recording starts when both are done. The countdown has focus (`activateForRecording`; Esc cancels), handed back to the recorded app when it ends. All of them `setVisibleOnAllWorkspaces(…, { skipTransformProcessType: true })` and the full theme. A recording that ends without a file (cancel, failure) restores like a cancelled overlay (`restoreFromOverlayCancel`).
- **`skipTransformProcessType` everywhere** (2026-11-24): without it Electron's `setVisibleOnAllWorkspaces` switches the app's process type on macOS (`visibleOnFullScreen` hides the Dock icon, without it shows it), which took the countdown's focus and popped an auto-hidden Dock up. `showDock` / `hideDock` track their own state (`dockHiddenByUs`; `app.dock.isVisible()` lied after such a switch). Consequence: Lumia's windows show over another app's full-screen Space only if they were up before it went full screen (capture / recording from inside full screen not supported; a per-session switch to a menu-bar app was built and dropped).
- **Close behavior**: clicking close on the main window hides to tray, on every page (2026-11-27: on `/editor` it used to go back to `/dashboard` and keep the window open, which read as a second window appearing; the window now resets to `/dashboard` and then hides, and the AppBar's Back is the way to the Dashboard). Real quit only via tray menu / `ExitLumia` hotkey / explicit `markQuitting()`. The main window comes back (shown and focused) on: launch (not at login), the menu-bar icon's Open Lumia / double-click, a Dock click, a second launch, a notification click, an image capture or recording (the editor, by Settings › General › Open Lumia after capturing or recording (`openLumiaAfter`, 2026-11-27): When it was open before (default: open before → back whatever happened, the editor after a success, its page after a cancel or failure; closed before → stays away), After a capture or recording / After a capture / After a recording (only after a success of that kind, open before or not), Never. `claimEditorAfterCapture(kind)` and `restoreFromOverlayCancel` in `index.ts`; kept away, the window counts as closed to the menu bar (system notification, focus back to the previous app); shown via `prepareMainOnRoute`, which draws the route at the overlays' parked opacity first so the hidden window's stale Dashboard frame never flashes), a cancelled overlay or a recording that ended without a file (again unless closed to the menu bar: then focus goes back to the previous app and the Dock icon stays hidden).
- **Single-instance lock**: `app.requestSingleInstanceLock()` prevents Chromium cache lock errors when relaunching while the tray instance is still alive.

### Persistence

Under the OS userData dir (`settings.json`, `templates.json` and `hotkeys.json` are electron-store files):
- `settings.json` — `AppSettings` (theme, default save path, active workflow, Google Drive tokens, last capture mode/kind — `lastCaptureKind` is `image | video | scroll`, history retention, `thumbnailVersion` / `thumbnailRefreshTries` (the one-time thumbnail refresh), last annotation style — `annotationStyle: { color, strokeWidth }`, written on toolbar picks and restored when the editor opens (the recording's drawing row reads and writes it too), `saveEditHistory` (keep the image editor's edit steps, default on), `keyToDrag` (image editor: the drag key + drag pans and Cursor draws a selection box; default off, Cursor pans), `openLumiaAfter` (`open` / `success` / `captures` / `recordings` / `never`, default `open`; `openEditorAlways`, `openEditor` and `openEditorAfterCapture` / `-Recording` before, all migrated), `copyAfterCapture` (default on), `recordCountdown` (0 / 3 / 5, default 3), `captureSelfWindow` (Settings › General › Show Lumia window), `captureFolder` + `pastCaptureFolders` (only through the folder dialog; `capture-folder.ts`), `wallpaperBefore` (for Reset wallpaper; never from the renderer), `trayActions` (capture actions in the menu-bar icon's menu, hotkey ids; default none), `editorKeys` (`{ image?, video? }`: only the editor keys the user changed, `{ actionId: binding }`; see `src/lib/editor-keys.ts`), custom theme picks `themeAccent` / `themeLightBase` / `themeDarkBase`, `showThemeButton` (the AppBar's moon / sun, default on; off, Settings › Appearance shows a Choose theme row))
- `edit-history/<id>.json` — the image editor's saved edit steps per row (see `edit-history.ts`)
- renderer `localStorage` (per-viewer conveniences): `lumia:history-filter`, `lumia:history-view`, `lumia:editor-views` (zoom + pan per image), `lumia:editor-history-pinned` / `-open`, `lumia:editor-stickers-pinned` / `-open`, `lumia:history-panel-width`, `lumia:annotation-custom-color`, `lumia.sticker.recents`, `lumia:wallpaper-screens` (the screen picker's last pick)
- `templates.json` — user workflow templates (built-ins are code-defined, never persisted)
- `history/YYYY-MM-DD.json` + `history_stat.json` — capture history, one file per local day plus totals (see `history-days.ts`; no row cap, the retention setting is the only limit; it covers the current save folder's history). A save folder other than the default has its own pair under `history-folders/<hash>/` (`folder-history.ts`). The old single `history.json` (an electron-store file, capped at 1000 rows) is moved into day files on first start and deleted, no backup (the capture files in `~/Pictures/Lumia` are the real data). Older builds don't read day files and show an empty history on the same profile. Thumbnails are **not** inline any more: each row's `thumbnailFile` names a JPEG under `userData/thumbnails/`, `history:days` / `history:recent` derive the `lumia-media://` URL the renderer puts in `<img src>` (so `loading="lazy"` actually defers offscreen previews — data: URLs never did), and rows from older builds that still carry a data-URL `thumbnailUrl` are moved to files on first start. A recording's filmstrip is `thumbnails/<id>-strip.webp` (`stripFile` on the row)
- `hotkeys.json` — `HotkeyConfig` with `schemaVersion` for forward migrations of capture-mode bindings

### Workflow pipeline

1. **Capture** — image or video. Originals always saved to the save folder, `{captureFolder()}/capture-{timestamp}.{ext}` (`~/Pictures/Lumia` by default; Settings › General › Save to, 2026-11-27). The `Save` button in the editor opens a Save-As dialog that writes a *separate* file via `runInlineAction('save')`.
2. **after-capture** steps: `annotate` (opens editor), `clipboard`, `save` (with empty `path` = surface a Save button only, don't auto-save).
3. **Upload** — destinations run in parallel via `Promise.allSettled`. Currently `r2` and `google-drive`.
4. **after-upload** steps: `copyUrl` (first/all), `openUrl`, `osShare`, `notify`.
5. **History merge** — when a workflow runs against an existing `historyId` (re-share from history), uploads merge by destination instead of creating a duplicate row.

### Build Tooling

- **electron-vite** compiles three targets (main / preload / renderer) — see `electron.vite.config.ts`. A build-only plugin there (`contentSecurityPolicy`, 2026-11-27) writes a Content-Security-Policy `<meta>` into both built pages (`index.html`, `overlay.html`): scripts from the app only, images from the app / `data:` / `blob:` / `lumia-media:` / `https:`, video from `blob:` / `lumia-media:`. Not in dev (the dev server needs inline scripts and a websocket). A new kind of resource the renderer loads needs a matching source there, or it's blocked in built apps only
- **Path alias**: `@/` → `src/` (renderer only)
- **Code shared by main and renderer** lives in `shared/` (in both tsconfigs): theme colours, wallpaper types and request constants, the watermark's numbers (`watermark.ts`), the default drawing colour (`annotation.ts` `DEFAULT_ANNOTATION_COLOR`, the one place it's written), the capture bars' top (`capture-bar.ts` `captureBarTop`), the recording frame rate (`recording.ts`: `RECORDING_FPS`, `recordingFps()`, `fpsFromFfmpegInfo()`), and setting values both sides list (`capture-settings.ts`: `OpenLumiaWhen`, the countdown values). One exception: main imports `src/utils/captureLabels.ts` (`formatDuration`, for the recording notification), listed by file in `tsconfig.node.json`'s `include`; it must stay free of DOM and Electron imports
- **Tailwind CSS 4** via `@tailwindcss/vite` plugin
- **electron-builder** packages to `release/`. Output: NSIS for Windows (x64 only — Windows-on-ARM runs it via emulation), DMG for macOS (x64 + arm64). `koffi` is `asarUnpack`ed so the FFI loader can read its native binaries at runtime; the `files` array drops koffi's prebuilt binaries for platforms we never package (keeps only win32_x64 + darwin_x64/arm64).
- `extraResources`: `resources/tray/*.{png,ico}` copied to `tray/` so the tray module finds icons in packaged builds; `extension/` copied to `Resources/extension` so users can Load-unpacked the scroll-capture browser extension (the `scroll-extension:open-folder` IPC opens it).
- **ffmpeg**: the afterPack hook (`build/after-pack.cjs`, which runs `embed-ffmpeg.cjs` and then `prune-locales.cjs`) embeds a per-arch ffmpeg into Resources. Lumia only runs `-c copy` remux / trim on WebM, so both platforms ship a **minimal matroska-only, LGPL-only build** (~2.5 MB):
  - **Windows** — cross-compiled with mingw-w64 via `build/build-minimal-ffmpeg-win.sh` (locally: `pnpm ffmpeg:min:win` → Docker; in CI the `ffmpeg-win` job uploads it as an artifact `release-win` downloads to `build/minimal-ffmpeg/dist/`).
  - **macOS** — compiled with clang via `build/build-minimal-ffmpeg-mac.sh` per arch (locally: `pnpm ffmpeg:min:mac`; in CI the `release-mac` job builds both arms — macos-latest is arm64, so x64 is cross-built via `clang -arch x86_64` — into `build/minimal-ffmpeg/dist/ffmpeg-darwin-<arch>`).
  - **Licence (Lumia is closed source):** the shipped ffmpeg must stay **LGPL v2.1+** — never `--enable-gpl` / `--enable-nonfree` / `--enable-version3` or an external library. Enforced twice: the build scripts' licence gate (checks `config.h`) and `embed-ffmpeg.cjs` (scans the binary's embedded configure line). There is **no fallback** to the ffmpeg-static download (a GPLv3 + x264/x265 build): packaging fails if no minimal binary is staged. `ffmpeg-static` is a devDependency used only by `pnpm dev`. The LGPL text + notice ship from `resources/licenses/` (extraResources → `licenses/`); bump `FFmpeg-NOTICE.txt` and the pinned `FFMPEG_SHA256` with any ffmpeg version change.
  - Keep the configure component flags, `FFMPEG_SHA256` and the licence gate in sync across the two build scripts.

## Platform-Specific Notes

- **Windows**:
  - WGC (Windows Graphics Capture) enabled via `--enable-features=WindowsNativeGraphicsCapture` for pixel-perfect screenshots
  - `setAppUserModelId('com.lumia.app')` must match `appId` in builder config — WinRT silently drops toasts otherwise
  - Mixed-DPI displays: `win.setBounds(displayBounds)` after construction to fix overlay placement on secondary monitors
  - Frameless with native `titleBarOverlay`; tray + global shortcuts via Electron defaults
  - Native input simulation via koffi FFI (no PowerShell)
- **macOS**:
  - No title bar: hidden inset, traffic lights at `(20, 19)` on the AppBar (14px circles on current macOS, so y 19 centres them on the 52px bar)
  - Universal builds (arm64 + x64); Graphics/Design app category; hardened runtime + entitlements via `build/entitlements.mac.plist`
  - Notarization is gated on `APPLE_*` env vars; `notarize.cjs` skips gracefully when absent
  - Frameless overlay-type windows (capture overlays, recording border, drawing layer) set `roundedCorners: false`; every `setVisibleOnAllWorkspaces` passes `skipTransformProcessType: true` (see Window Management). Full-screen apps: capture / recording started inside another app's full-screen Space isn't supported; the menu-bar icon's menu works there (`tray.ts`)
- **Capture timing**: `HIDE_DELAY_MS` is 250 ms on macOS / 200 ms on Windows after hiding overlay/main windows before requesting frames (recordings don't wait at all since 2026-11-24: nothing is recorded before the countdown ends) — ensures a clean screen capture. On macOS the freeze skips the hide wait entirely when the `screen-snap` helper is active (the snapshot excludes Lumia's windows by PID at the compositor level); `freezeAllDisplays` re-inserts the wait if it unexpectedly lands on the desktopCapturer fallback.
- **Auto-update**: `electron-updater` polls the Cloudflare R2 origin (`generic` provider, defaulting to `https://release.lumia.asia` — `latest.yml` / `latest-mac.yml`) every 4 hours in production builds. A check is not consent (2026-11-22): Settings › About shows the new version with **Update** (downloads) then **Restart** (installs); once downloaded the "New update downloaded" toast offers Restart too and stays until closed; no install on quit. Silent download + install only with Settings › About › **Auto-update Lumia** on (`autoUpdateWhenHidden`, default off; titled "Auto-Update while hidden" until 2026-11-24). Status events surface in the renderer via `update:status` and the `UpdateNotification` component.

- `MAIN_VITE_GDRIVE_CLIENT_ID`, `MAIN_VITE_GDRIVE_CLIENT_SECRET` — Google Drive OAuth
- `MAIN_VITE_GDRIVE_API_KEY`, `MAIN_VITE_GDRIVE_PROJECT_NUMBER` — Google Picker API (in-app Drive folder browser)

`RENDERER_VITE_*` vars are baked into the **renderer** bundle instead (electron-vite exposes them via `import.meta.env`; typed in `src/vite-env.d.ts`):
- `RENDERER_VITE_CHROME_WEB_STORE_URL` — public Chrome Web Store listing for the scroll-capture extension; the Dashboard's "Add to Chrome" setup button appears only when set.

These are **not** user-facing settings — distributing the app means embedding R2/Drive credentials in the bundle. Per-user state (refresh tokens, folder IDs) lives in `settings.json`.
